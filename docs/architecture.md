# Architecture

This document maps the package for developers and AI agents.

## Layers

```
choices/        Plain constants: Tailwind/DaisyUI class choices
base_blocks/    Reusable design primitives and the block CSS pipeline
blocks/         Public block composition built on base_blocks
models/         DaisyUITheme + theme orderables/fields (core app)
assets/         DaisyUIIconSource, DaisyUIFavicon snippets + view sets
menus/          DaisyUIMenu snippet + view set
feeds/          Feed snippet, data blocks + view set
icons/          Icon provider registry, chooser field/block/widget
dynamic/        Context models, dynamic image/link values, resolution,
                actions (code only; see `action_blocks.py`)
detail_pages/   ModelDetailPage/ModelDetailTemplate + post_save/pre_delete
                bridges (see docs/detail-pages.md)
approval/       Approval workflow registry + pre_save/post_save bridges
favicon/        Public manifest.json / browser-config.xml / favicon.ico views
notifications/  Email templates, bridges, audiences, campaigns, email_blocks/
forms/          DaisieFormPage and the DaisyUI form builder
errors/         Admin-designable error pages and Django handlers
allauth_ui/     Opt-in DaisyUI templates for allauth pages and forms
allauth_emails/ Opt-in AllauthEmailOverride snippets (see docs/allauth.md)
help.py         In-admin "DaisyUI Editor Guide": index + per-topic pages
help_reference.py  Generates the guide's block reference from the registries
templates/      Block, tag, admin and preview templates
middleware.py   ArbitraryCSSMiddleware: runtime CSS for arbitrary colours
tailwind/       Tailwind + daisyUI input CSS and the generated safelist
static/.../css/daisie.css  Committed, prebuilt Tailwind + daisyUI stylesheet
```

## Apps and migrations

The distribution is one package split into per-feature apps (core,
`assets`, `menus`, `feeds`, `errors`, `notifications`, `allauth_ui`,
`allauth_emails`), each with its own `migrations/` and explicit `label`.
`notifications`, `allauth_ui` and `allauth_emails` are opt-in:
`notifications` and `allauth_emails` are extra-installed (see the README), and
the optional view sets are guarded with `apps.is_installed()` in
`wagtail_hooks.py`. Register all apps in `INSTALLED_APPS` before project apps
(and before `allauth`).

### `dynamic/`

`registry.py` parses `WAGTAIL_DAISIE_CONTEXT_MODELS`; `resolvers.py` resolves
request/URL/fixed values and dynamic expressions (including the URL scheme
allow-list); `mixins.py` injects the values into page and block contexts;
`blocks.py`/`forms.py` provide the per-page binding chooser; `feeds.py`
implements typed filters and feed rendering; `action_blocks.py` defines the
Action struct (a normal button subclass plus a confirmation alert);
`actions.py` + `urls.py` + `views.py` run developer-defined actions (adding the
confirmation to Django messages) and serve feed slices. This package is
code-only: the `Feed` model lives in the `feeds` app and the Feed/Calendar
blocks in `feeds/blocks_data.py`.

### `tailwind/` / `middleware.py`

`tailwind/input.css` is the Tailwind source (`@plugin "daisyui"` + the extended
typography scale + `@import "./safelist.css"`); `tailwind/safelist.css` is
generated by `manage.py daisie_safelist` from `choices/*` and the feed layout
literals. `just build-css` compiles the committed
`static/wagtail_daisIE/css/daisie.css`, linked with `{% daisyui_styles %}`.
`middleware.py` (`ArbitraryCSSMiddleware`) generates CSS for arbitrary colour
utilities at request time. See [assets.md](assets.md).

### `detail_pages/`

`registry.py` parses `WAGTAIL_DAISIE_DETAIL_PAGES`; `models.py` provides the
abstract `ModelDetailPage` and `ModelDetailTemplate` page types; `bridges.py`
connects `post_save`/`pre_delete` receivers (wired in `apps.py`) that create,
update and delete a generated page for each model record. Deletion runs in
`pre_delete` because a `GenericRelation` cascade fires outside Wagtail's page
tree bookkeeping.

### `approval/`

`registry.py` parses `WAGTAIL_DAISIE_APPROVAL_WORKFLOWS`, resolving each source
model and handler lazily; `bridges.py` connects a `pre_save` receiver that
snapshots the approval field and a `post_save` receiver that runs the project
handler once on `False → True`, recording the result in `converted_field` for
idempotency. Bridges connect in core `AppConfig.ready()` inside `try/except`.
See [approval.md](approval.md).

### `favicon/`

`views.py` serves the manifest, `browserconfig.xml` and `favicon.ico` for the
active `DaisyUIFavicon` snippet (`models/favicon.py`); `urls.py` wires them up.
The snippet tag `{% daisyui_favicon %}` renders the `<link>`/`<meta>` tags into
the document head.

### `allauth_ui/`

Opt-in DaisyUI templates for django-allauth's account pages. The package never
ships a `base.html` to be shadowed: `templates/allauth/layouts/base.html`
extends `WAGTAIL_DAISIE_ALLAUTH_BASE_TEMPLATE` (defaulting to the package's own
`wagtail_daisIE/allauth/base.html` chrome), so a project can point allauth at
its own site chrome. `context_processors.py` maps the allauth base template back
to the template that extends it, which keeps parent-base detection working for
subclasses. `wagtail_daisIE/allauth/base.html` is a bare DaisyUI shell — it
deliberately has no page body of its own. `models.py`/`blocks.py` provide the
`AllauthPageOverride` snippet and its `auth_form`/`auth_field` blocks;
`catalogue.py` discovers account views/forms; `sync.py` + the
`check_allauth_templates` command keep the per-template overrides in sync with
allauth. See [allauth-pages.md](allauth-pages.md).

### `notifications/`

`placeholders.py` renders `{{ ... }}` expressions (Django engine, autoescape,
tags left literal); `context.py` builds the built-in context;
`email_rendering.py` turns an `EmailTemplate` into subject/HTML/text;
`mjml.py` + `email_blocks/` provide the MJML component blocks; `bridges.py`
dispatches events; `registry.py`/`conf.py` read bridge settings; `campaigns.py`
sends audiences; `models.py` holds `EmailTemplate`, `Audience`,
`AudienceMember`, `EmailCampaign` and `CampaignRecipientLog`. The allauth
email overrides live in the `allauth_emails` app (`allauth.py`,
`catalogue.py`).


### `choices/`

Pure data: `DAISYUI_BG_COLOR_CHOICES`, `FONT_SIZE_CHOICES`, `PADDING_CHOICES`,
etc. No Django imports beyond `gettext`.

Each constant is a `choicelist.ChoiceList` — a callable `list` that
deconstructs to a short registry key, `get_choice_list("<KEY>")`. Wagtail stores
a callable `choices` argument by reference, so the option lists stay out of the
frozen StreamField `block_lookup` in migrations instead of being written out
verbatim. Add new constants as `ChoiceList(...)` assigned to a module-level name
(the key must be unique); model fields, which Django materialises from an
iterable, are passed a plain zero-arg function returning the list. The test
`tests/core/test_choice_lists.py` enforces this.

### `base_blocks/`

Design primitives that can be composed into any block:

- `size.py` — width/height/size and media aspect.
- `box.py` — padding, margin, border, rounded corners, shadow, spacing.
- `background.py` — `TextBackgroundBlock` (solid colour; email-only).
- `typography.py` — `TypographyBlock` (colour, font family, size, weight,
  alignment, line height, letter spacing, underline + colour/thickness, and
  `hover`/`active` states via `TypographyStateBlock`).
- `background_layer.py` — `BackgroundStreamBlock`/`BackgroundLayerBlock`:
  solid/image/gradient layers used by all web design composites (rendered as an
  inline `block_style`) and for page/menu/allauth backgrounds.
- `audience.py` — `AudienceBlock` plus `evaluate_audience`.
- `link.py` — `LinkDestinationBlock`, `AbstractLinkBlock`, `link_url`.
- `markup.py` — `InlineMarkupBlock` + `render_inline_markup`/
  `strip_inline_markup` for rudimentary inline markup.
- `design.py` — the design composites (`DesignBlock`, `TypographyDesignBlock`,
  `MenuItemDesignBlock`, `MainDesignBlock`, ...) and the `Themed*Block` bases
  that produce `block_css` and `audience_allowed`.
- `css.py` — pure functions that turn design values into class strings, plus
  `merge_block_css`.
- `mjml.py` — email counterpart of `css.py`: turns design values into literal
  CSS declarations for MJML output (see [emails.md](emails.md)).
- `fields.py` — `ColorChoiceBlock`, `FontFamilyChoiceBlock`.
- `widgets.py`, `utils.py` — helpers.

### `blocks/`

Composes `base_blocks` into editor-facing blocks: `content.py` (`ContentBlock`),
`content_blocks.py` (`PAGE_CONTENT_BLOCKS`), `cards.py`, `inline.py`, `link.py`,
`layout.py`, `layout_components.py` (hero, drawer, stack, aura, indicator, mask,
dropdown, swap, tabs, carousel, pagination, FAB, filter, join), `display.py`
(badge, kbd, divider, avatar, stat, countdown, skeleton, text-rotate, chat,
timeline, diff, hover-gallery/3d), `mockups.py`, `breadcrumbs.py`, `marquee.py`,
`media.py`, `spaced.py`, `accordion.py`, `blockquote.py`, `menu_items.py`. The
package `__init__` imports the heavy composition modules lazily to avoid an
import cycle with `dynamic.action_blocks` (cards and menus both expose the Action
block). Cards may contain an Action block, and either a button or an action can
set `make_parent_clickable` to turn the whole card into its click target.

## The `block_css` pipeline

1. A block's `Meta` declares a `design` field made of primitives.
2. `ThemedBlock.get_context` calls `build_design_css(value["design"])` to get a
   space-separated class string, then merges it with any `block_css` inherited
   from `parent_context`. The `design.background` stream is rendered separately
   into `block_style` (`background: …`).
3. The block template receives `block_css` (into `class`) and `block_style`
   (into `style`).

Menu defaults use this: `DaisyUIMenu.get_item_css()` returns the classes for
`item_design`, and the menu templates wrap their item loop in
`{% with block_css=menu_item_css %}`. Each item then appends its own classes.
Because both are plain utility classes, per-item classes come last and win
where stylesheet order allows.

## Page rendering

`StyledPageMixin` adds `page_theme`, `page_background`, `page_design`,
`main_design`, and `body`. Its `get_context` injects `daisyui_theme`,
`daisyui_page_background_css`, `daisyui_main_css`/`daisyui_main_style` (resolved
from the page's `main_design`, falling back to the theme's) and the
per-category default channels (`container_css`, `text_css`, `button_css`,
`media_css`) built from `PageDesignBlock`. Each `ThemedBlock` inherits only its
own category channel, keeping defaults isolated. Page templates render
`{% daisyui_theme_full_css daisyui_theme %}` in `<head>`, apply
`daisyui_page_background_css` to the body, and put
`{% daisyui_main_attrs daisyui_theme %}` on `<main id="main-content">`; body
blocks must be rendered with `{% include_block %}` (as `home_page.html` does) so
they receive the page context.

## Menus

`DaisyUIMenu` is a `ClusterableModel` snippet with revisions and preview. It
stores `branding`, `item_design`, and `body`, and is rendered by the
`daisyui_menu` inclusion tag. See [menus.md](menus.md).

## Errors

`errors/models.py` defines the status-specific `ErrorPage` snippet and
`errors/view_sets.py` registers **Errors → Error pages** in the Wagtail admin.
`errors/handlers.py` selects the active page, resolves its explicit or default
theme, and renders `templates/wagtail_daisIE/errors/error_page.html` with the
original HTTP status. Projects opt in from their root URL configuration, while
audience-gated pages can render the 403 snippet directly. See
[error-pages.md](error-pages.md).

## Icons

Provider-based registry; see [icons.md](icons.md).

## Invariants

See `AGENTS.md`. The most important are: no database queries at import time, and
nesting a `StreamBlock` inside a `StructBlock` by using the block instance
(never `StreamField`, which is a model field).

## Tests

`tests/` runs against `wagtail_daisIE.test.settings` (package only). Tests that
need the demo `home`/`blog` apps live in `demo/`.
