# Roadmap

## CSS delivery: guaranteed Tailwind coverage without a hand-maintained safelist

### Current state

`daisie.css` is prebuilt from `tailwind/input.css` plus a generated
`tailwind/safelist.css`. The safelist exists because block classes are composed
at runtime (`block_css`). It is generated by `manage.py daisie_safelist`, but
the generator historically only walked `list`/`tuple` constants. Dict-based
choices (padding, margin, gap, main layout) and integer-driven classes (border
width, table border spacing) were therefore missing. Phase 1 fixes that.

### Phase 1 — Safelist correctness (now)

- Recursively collect values from lists, tuples and dicts; split multi-class
  strings into individual tokens.
- Fail the command when a name in `choices.__all__` is missing or unresolved.
- Add integer-driven ranges: `border-2..999`,
  `border-spacing[-x/-y]-1..96`, `md:grid-cols-1..6`.
- Add template-composed classes: `alert-*`, feed layout literals, table/button
  literals.
- Fix `build_border_css` to emit `border-solid`; stored values stay unchanged.
- Add a generated-file drift test and a coverage test for every choice family.
- Regenerate `safelist.css` and `daisie.css`.

### Phase 2 — Builder-derived manifest

Replace the committed safelist with a temporary content file generated by
calling the real builders (`build_design_css`, `build_typography_css`, ...)
across every choice value and variant. Nothing hand-maintained is committed;
coverage follows the render path by construction. Keep the committed
`daisie.css` for downstream consumers.

### Phase 3 — Live authoring

Add an optional dev-only collector that appends rendered class tokens to a file
watched by `tailwindcss --watch`, so admin edits rebuild CSS immediately.
Production remains prebuilt.

### Phase 4 — Optional request-time JIT (opt-in)

If production must react to classes that cannot be enumerated at build time, add
a sidecar compiler service alongside Django:

- Node service using `@tailwindcss/node` + `@tailwindcss/oxide`, warm compiler,
  `source(none)`, fixed input CSS owned by the service.
- Django sends only candidate tokens; never CSS, `@import` or `@plugin` paths.
- Unix socket / localhost only, read-only filesystem, no network egress,
  resource and candidate caps, short timeout.
- Cache by hash of the candidate set + input CSS + plugin versions.
- Fail open to the committed `daisie.css`; never render unstyled pages.
- Candidate policy required: arbitrary values (`bg-[url(...)]`) can generate
  external requests, so reject or allowlist them.
- Not enabled by default; downstream projects must provide the service and
  binary. `@tailwindcss/node` is undocumented and must be version-pinned.

`wagtail-asset-publisher` is not used: it compiles per page at publish time,
covers only Wagtail page serves, and is outside its tested Wagtail/Django
matrix.

### Non-goals

- Browser-side `@tailwindcss/browser` in production (Tailwind marks it
  development-only).
- A runtime Node requirement for the package's default install.
- Per-page CSS duplication of daisyUI and the typography scale.

## Menus: submenu container design

### Current state

Megamenu submenu panels (popover containers) are rendered with fixed classes
and have no dedicated design StreamField. `menu_design` covers the outer
container and `item_design` covers individual items, but submenu panels cannot
be targeted independently.

### Planned

- Add a `submenu_design` (or reuse a spaced design block) to `DaisyUIMenu`.
- Wire it into `megamenu.html` for the popover panel.
- Support responsive overrides for submenu containers.
